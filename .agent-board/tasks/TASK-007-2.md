# TASK-007-2 - Read-Only Karma Ledger and Ratings Inspection

Status: Backlog
Priority: P1
Project: Take Me Pic Web/Admin
Milestone: Web Phase 1 - Admin trust and safety foundation
Owner: Agent

## Purpose

Give staff read-only inspection of how a user earned karma and how they were
rated, as fraud/abuse-investigation context. Companion to the mobile karma
leaderboard and rating feature being built next in the mobile repo.

## Scope

- Add a karma ledger section (delta, reason, linked help request, date) to
  the `/admin/users/[id]` detail view.
- Add ratings context (stars given/received, comment text, linked session)
  to the user detail and session review views.
- Inspection only: no karma adjustments, no rating moderation mutations.
- Out of scope: `/admin/leaderboard` (derived view, defer to TASK-009
  analytics), `/admin/karma/rules` (earning rules live in mobile app logic;
  no backend to edit), `/admin/badges`.

## Acceptance Criteria

- [ ] Staff can read any user's karma ledger; non-staff users still read only
      their own ledger.
- [ ] User detail shows recent ratings received with stars and comments.
- [ ] Staff-only access is enforced server-side.
- [ ] `npx tsc --noEmit` passes.
- [ ] `npm run build` passes.

## Technical Notes

- `karma_ledger` (`user_id`, `delta`, `reason`, `help_request_id`,
  `created_at`) currently has only `karma_ledger_self_read`
  (`auth.uid() = user_id`) — needs a `karma_ledger_staff_read` policy
  (`private.is_staff()`), same pattern as `help_requests_staff_read`
  (ADR-0004). Plain lifecycle data: RLS policy, not an RPC.
- `ratings` (`help_request_id`, `rater_id`, `ratee_id`, `stars`, `comment`)
  is already readable by any authenticated user, so no policy change.
- `ratings.comment` is free text and can be abusive, but a rating is not a
  valid **Report target** today (reports point at user/post/comment/session/
  conversation/message). If rating moderation is needed, that is a schema +
  glossary decision to coordinate with mobile — flag it, don't build it here.
- `leaderboard` is a derived view (rank, karma, profile fields); reading it
  in admin adds nothing operationally over `profiles.karma`.

## Dependencies

- TASK-005 completed (user detail view exists).
- Coordinate timing with the mobile karma/rating feature work so both clients
  read the same `karma_ledger` / `ratings` semantics.

## Verification
